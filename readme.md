# Individual-Level Persistence and Advancement Among Quota-Elected Women in Italian Municipal Politics

Replication package for the Computational Social Science final exam
paper (MSc Data Science, University of Trento). This README exists so
that a stranger, or a random professor willing to give a good grade to
an exam, can reproduce every number in the paper without having to
reverse-engineer it from the paper. The paper itself (LaTeX source and
compiled PDF) is submitted separately from this repository; this repo
is the code and data side of the submission.

## Project Objective

I built an individual-level panel of every Italian local administrator
from 1986 to 2026 (sindaci, vicesindaci, assessori, consiglieri)
from Ministry of Interior open data, and used it to ask a
question the existing literature on Italy's 2012 gender-quota law
hasn't: not "did the quota increase the share of women elected"
(answered, repeatedly, by better-funded people than me), but "do the
women who get elected via the quota actually build careers, or is it a
revolving door?" Short version of the answer: they don't get pushed out
faster than men (a real, if modest, finding against a naive tokenism
story), but they do advance up the hierarchy less.
A little spoiler: Parties don't seem to be quietly overcompensating for this quota
by recruiting more of their brothers-in-law. An exploratory extension
digs one layer deeper and finds the advancement gap concentrates almost
entirely among women without pre-existing political-family ties, which
points at access and sponsorship, not sex per se, as the likely
mechanism. Full details, appropriately hedged, in the paper ;)

## Prerequisites

Developed and tested with Python 3.14 (confirmed from local traceback
paths during debugging; if you're on something significantly older,
that's the first thing to check if you hit an error nothing else here
explains).

```bash
pip install pandas numpy lifelines statsmodels pyarrow matplotlib seaborn
```

`pyarrow` is required for the caching layer (Parquet). `matplotlib` and
`seaborn` are only needed for `graphics.py`; the other three scripts
don't touch them.

No exact package versions are pinned above, which is a real gap for
strict reproducibility, not just a formality: a future pandas/statsmodels
release changing a default could plausibly break something here without
warning. If you want to remove that risk before submitting, run
`pip freeze > requirements.txt` in your working environment and include
that file alongside everything else.

## About the data

**The raw source files are already included in `data/raw/`** -- you do
not need to download anything to reproduce the analysis. They come from
the Ministry of Interior's historical administrator archive
(`dait.interno.gov.it`), named `storico_amministratori_comuni_DDMMYYYY.csv`
(year-end snapshots, 31 December, plus one live snapshot -- mine is
`storico_amministratori_comuni_24082026.csv`).

Worth knowing even though you won't need to repeat it: the source
portal actively blocks automated/bot requests, so these were downloaded
by hand, one at a time, which is also why they're bundled here rather
than fetched by a script -- there's no reliable way to automate that
step, and I'd rather ship the actual files than a download script that
won't work.

A couple of things about the raw files themselves, in case you ever
need to refresh them with a newer year:
- **Naming is inconsistent across years**: 2014 and 2015 use an
  underscore before the date (`storico_amministratori_comuni_31122015.csv`),
  other years generally don't. Both patterns exist in what's bundled
  here; `panel.py`'s file-loading loop expects the exact names present
  in `data/raw/`, so if you add a new year, check which pattern it
  actually uses rather than assuming.
- **2023-2025 use a genuinely different field schema**
  (`data_inizio_carica`, `funzione`,
  `popolazione_censita_alla_data_elezione`, etc.) and the live snapshot
  has no cessation-date field at all, by definition, since everyone in
  it is still serving. Both are handled automatically via column
  aliasing and schema validation in `load_storico()` (inside
  `panel.py`), not excluded.

**`data/preprocessed/` ships empty, deliberately, not by oversight.**
The pipeline builds a cached panel there (`full_panel.parquet`) that I
would have included directly, since it would save you the ~6-minute
rebuild, but it's too large for GitHub's file-size limits. The only
consequence is that your first run of `panel.py` will take the full
~6 minutes to rebuild it from the raw CSVs already sitting in
`data/raw/`; every script after that reuses the cache and runs in well
under two minutes. Nothing to configure, nothing to fix, just a wait
the first time.

## Running it

```bash
python panel.py                  # Primary analysis: builds the panel,
                                  # runs descriptive diagnostics,
                                  # bandwidth robustness sweep, Cox
                                  # model, logit models
python dynastynet.py             # Secondary analysis: dynastic
                                  # recruitment (H3)
python graphics.py               # All figures and tables, including
                                  # the exploratory extension -- these
                                  # feed the separately submitted paper
python dynasty_crossreference.py # Optional: exploratory dynasty x H2
                                  # interaction on its own, standalone
                                  # console output (graphics.py already
                                  # calls this internally too, so you
                                  # don't strictly need to run it
                                  # separately unless you want to poke
                                  # at it in isolation)
```

Run `panel.py` first -- every other script reuses its cached panel
(`data/preprocessed/full_panel.parquet`, rebuilt automatically on that
first run since it isn't shipped, see above) rather than rebuilding
from scratch.

**Expected runtime**: roughly 6 minutes for `panel.py` on the full
1986-2026 panel (measured: 348.5s) on that first run, since the cache
has to be built from the raw files. Subsequent runs against the
now-existing cache are much faster, since the expensive part (parsing
40-odd CSVs with per-file encoding detection and schema validation)
only has to happen once. `dynastynet.py` and `graphics.py` each run in
well under two minutes once the shared cache exists.

### Verifying you actually reproduced the results

Rather than eyeballing whether "the numbers look about right," check
these specific values, since they're the ones the paper's Abstract and
Results section build on directly:

- `panel.py`, Cox model section: N should read **858,407**, and the
  within-sex decomposition should read **+10.2% (men) / -0.1%
  (women)**.
- `panel.py`, baseline climb logit: within-sex decomposition should
  read **+26.9% (men) / +6.0% (women)**.
- `panel.py`, flexible climb logit: within-sex decomposition at the
  cutoff should read **+30.9% (men) / -2.8% (women)**.
- `dynastynet.py`, baseline model: within-status decomposition should
  read roughly **+31.0% (below threshold) / +24.6% (above threshold)**,
  with the interaction term non-significant (p > 0.05) in all three
  specifications (baseline, top-1%-excluded, top-5%-excluded).
- `dynasty_crossreference.py` (or the equivalent section of
  `graphics.py`'s output): the four-group decomposition should read
  **+30.4% (male, non-dynastic) / +12.6% (male, dynastic) / +4.4%
  (female, non-dynastic) / +12.7% (female, dynastic)**.

If your numbers are close but not identical (fractions of a percentage
point off), that's most likely floating-point/library-version noise,
not a real discrepancy -- see the Reproducibility note below. If
they're substantially different, something's actually wrong, and the
most likely cause is a stale cache or a code modification made after
the fact, not a logic error in the shipped code itself.

## Things that will bite you if you don't read this part

- **The cache is a trap if you change the pipeline logic.** If you
  modify anything upstream of `stack_years()` in `panel.py` (encoding
  handling, dedup rules, column aliasing, the entity-resolution key,
  the entity-quality filter below) after `data/preprocessed/full_panel.parquet`
  already exists, delete it first, or every downstream script will
  silently keep analyzing data built under the old logic with no error
  to tell you so. I found this out the educational way. More than once.
- **Encoding is not consistent across 40 years of government CSVs.**
  Some files are `cp1252`, some are `utf-8`, at least one has a BOM
  that will break a naive parser. `load_storico()` (in `panel.py`)
  tries a fallback chain (`utf-8-sig` -> `utf-8` -> `cp1252` ->
  `latin-1`, in that order specifically, since `utf-8-sig` handles
  files with or without a BOM correctly and a naive `utf-8` attempt
  does not) and reports which one worked for each file.
- **Column names aren't consistent across years either.** Beyond the
  2023-2025 schema change, the live snapshot renames the comune field
  (`denominazione_comune` instead of `descrizione_comune`) and the
  birthplace field (`luogo_nascita` instead of `sede_nascita`), both
  handled via an explicit alias map in `load_storico()`.
- **Two data-quality filters run centrally, once, in `stack_years()`,
  before dedup**: rows with an incomplete entity-resolution key
  (missing cognome/nome/data_nascita) get dropped, since a shared
  "MISSING" placeholder risks silently merging two different people;
  and any `person_key` whose recorded sex is inconsistent across
  appearances gets dropped entirely, for the same reason. Both are
  logged with counts when they fire, and every downstream script
  inherits this same cleaned entity set automatically.
- **The most recent (live) snapshot has no cessation date, by
  definition**: everyone in it is still serving. This is handled
  correctly (treated as right-censored), not as missing data, but if
  you're staring at the output wondering why that file contributes zero
  "events" to the Cox model, that's why, it's a feature, not a bug!
- **The dynasty-detection surname match is a proxy, not verified
  genealogy**, and uses a fixed 20-year lookback window specifically
  because an earlier "ever since 1986" version turned out to be
  mechanically confounded with calendar time (details in the paper's
  Limitations section, and in `dynastynet.py`'s docstrings if you want
  the blow-by-blow). If you change `window_years`, expect the post-2013
  coefficient to move, and that's expected, not a red flag; treat it as
  a sensitivity check.
- **Standard errors everywhere are nonrobust, not clustered.**
  Clustering by comune was the intended specification (lots of
  observations share a municipality) and was implemented and tested
  across all three model classes, including a faster HC1/robust
  fallback tried as a middle ground, but it reproducibly caused
  prohibitive computation time and got reverted rather than shipped
  half-tested. If you ever pick this back up: the attempt lived in the
  Cox model function in `panel.py` (lifelines `cluster_col`/`robust=True`)
  and the statsmodels logit functions across `panel.py`, `dynastynet.py`,
  and `dynasty_crossreference.py` (`cov_type='cluster'`/`'HC1'`). One
  specific bug to watch for if you retry it: lifelines'
  `CoxPHFitter.fit()` treats *every* column in the dataframe you hand it
  as a covariate (unlike statsmodels' formula-based fitting, which only
  uses columns you actually name), so a leftover cluster-ID column left
  sitting in the dataframe after removing the clustering parameter gets
  silently fit as a spurious regressor. This genuinely happened once
  during development, quietly shifted the Cox model's N and
  coefficients, and only got caught by comparing against a known-good
  run. If you re-add a cluster-ID column for any reason, make sure it's
  dropped from the covariate set explicitly, not just from the
  `.fit()` call's arguments.
- **`dynasty_crossreference.py` is draft-quality relative to the other
  three scripts.** It's been run and cross-checked against the paper's
  numbers, but it hasn't been through the same many-round iterative
  debugging the primary pipeline has. Treat any further changes to it
  with proportionally more suspicion.

## Reproducibility note

Every number quoted in the paper corresponds directly to a printed line
in these scripts' output: I did not hand-copy anything through an
intermediate spreadsheet, which is exactly the kind of step where
transcription errors like to hide. If a number in the paper doesn't
match your own run, the most likely explanations, in order of
probability, are: (1) your cache is stale relative to a code change,
(2) something got modified between what's described here and what's
actually in the files, (3) something in the Ministry's data changed
since I downloaded it (it happens, and I wouldn't be surprised given
the data entry and annotation quality, or lack of, showcased throughout
the datasets).
